# Prepared Browser Rehearsal

## Before timing

Resolve environment problems outside the take: official server/origin, lifetime
beyond an interactive tool call, real resource/schema reads and capabilities.
Do not invent ports or replace APIs with fixtures. For authorized host persistence
changes use the canonical adapter and disclose scope: development-wide local
storage affects preferences/forms as well as pages, and proves neither remote
ui_user_config nor ETag. Do not silently change persistence to meet a time target.

Prove a temporary component can load real data, save and reopen after reload;
remove it through the controls. Show the empty page and keep its checkpoint.
Prepare only snippets permitted by the agreed lane. No-JSON exercises stay
no-JSON. When JSON is allowed, disclose prepared per-component snippets versus
discovering/writing them during the take. Do not clear other pages, preferences
or domain records to obtain a blank canvas.

## Run and measure

Start after readiness and point zero. Stay in one visible tab; all authoring goes
through editors. No source patches, Angular state injection, direct storage edits
or completed-page restore during the take. Pasting into an allowed visible JSON
field is a normal editor operation.

Record phase times for data, content, layout, interactions and verification.
Label cumulative milestones versus phase durations so they are not added twice.
Ordinary timestamps suffice; do not create new product telemetry. Network,
rendering and capability waits count as elapsed time.

A proposed budget for a five-minute collection-screen run is below. It is a
target, not a measured distribution:

| Phase | Budget | Exit condition |
| --- | ---: | --- |
| Resource, sources and state | 45s | Real inputs bound, examples identified |
| Header and collection content | 90s | Required components present/editable |
| Layout and visual treatment | 40s | Desktop/mobile configured |
| Filter/action connections | 60s | One query and declared actions |
| Journey verification | 65s | Counts, clear, pagination, detail and mobile |

Adapt to the requested job. Do not omit proof to hit 300s. Report preparation
separately and compare like-for-like runs. A Hero HQ rc.17 prepared run on
2026-10-15 measured 396.75s with component JSON, real reads and native local
configuration. One run is not a median, novice benchmark or achieved five minutes.

A later take measured 629.446s; it spent rework on an accidental palette insertion,
uncommitted connection paths and layout. Its persistence priority was corrected
only post-take, so it is not a fully equivalent timed success. Avoid that rework
with per-component origin selection, verified focus/panel readiness and immediate
saved-path checks from the collection reference. Never remove these checks to
meet the time target. Any post-take correction stays outside the timed result and
must be disclosed; completion requires the agreed quality as well as elapsed time.

Subsequent prepared collection-screen runs measured251.710s and228.780s with
real reads and the agreed fidelity. These prove those specific takes, not a
five-minute benchmark for a larger dashboard. A thirteen-widget dashboard with
four statistics sources and multiple links needs its own full measurement.

## Interruptions and closure

Normal waits and editor navigation belong to the flow. Server restart, navigation
recovery, source repair or checkpoint restore interrupts a continuous take. Mark
it interrupted, diagnose outside timing, then restart from an authorized point
zero when the user still wants a continuous take. If the official API does not
recover, preserve checkpoint, logs and elapsed time and report the blocked proof;
do not claim completion or substitute mocks. Do not silently exclude failures.

End after the agreed preview/interactions. Save screenshots and a sanitized page
document via product export/inspection. Label any later reload/regression checks
as post-take. Keep the deliverable tab, reset temporary viewport overrides and
state any retained server. Do not claim a recording unless one was made.

After at least three comparable runs report median, range, preparation and quality.
Improve the slowest measured phase. Native compositions/presets and fewer repeated
dialogs improve the product; faster typing alone does not prove learnability.

## Diagnose live apply separately from reload

Before a new timed run, test a newly inserted page-owned collection with resource
and configuration applied together. After Apply JSON and Save, inspect both the
reopened document and the settled runtime: title/toolbar, inline filters, columns,
page size and actual row count. Then save the page and reload for comparison.
A successful round trip does not prove live apply; a loading frame does not prove
a persistent defect. Use the same widget and record each observation's stage.

In the 2026-10-15 employee-360 take, toolbar recovery followed reload. Two isolated
rc.26 controls later rendered the toolbar and three filters before reload, including
the full table configuration. Thus the toolbar-only cause was not reproduced and
must remain uncertain. The fresh full configuration did show a different mismatch:
JSON pageSize5 versus10 rendered rows after async loading; reload restored5.
A subsequent5→3 edit briefly showed3, then settled back to5 while its editor
still saved3; reload restored3. A further3→4 JSON edit sent the old request size3
and received response size3: compare transport metadata before blaming rendering.
Table ngOnChanges fetched before synchronizing its runtime pageSize with config.
Keep immediate and settled observations distinct; do not teach mandatory reload as a product requirement.

Readiness must include usable capabilities for every operation promised in the
take. Real list reads with an expired session and disabled New prove consultation,
not form writes. Do not bypass permission or quietly reduce the agreed journey.
Check state-path discovery with persist:false before multiplying related surfaces.

Measure last authoring Save, final interaction, formal stop and post-take evidence
separately. One employee-360 run last saved at543s but formally stopped at617s;
that is not a fully verified under-ten-minute success. Keep the timed page frozen.
Use an isolated page identity for diagnosis, preserving original and take configs.

For paired visual proof use the same per-tab viewport and equivalent list/dossier
positions, close obstructing navigation and confirm the DOM has settled before
capturing. An inner-scroll application can produce viewport-only fullPage captures;
label the extent honestly and capture the dossier separately. Reset viewport
emulation after comparison. Post-take screenshots never move work inside the timer.

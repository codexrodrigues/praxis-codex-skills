# Compose Pages And Hosted Widgets

Inspect the installed `DynamicPageBuilderComponent`, palette metadata and actual
host entrypoint. Use the browser-workflows capability ledger to select child
skills; load the relevant owner before configuring its document. A newer source
checkout does not prove the installed editor exposes the same controls.

## Page, Shell And Content

1. Establish page identity, current widgets, permitted side effects and persistence.
   Inspection does not authorize adding test widgets. Insertion or applying a
   child editor can propagate `pageChange` into autosave before the page Save button.
2. Open customization through the host's visible entrypoint. Insert a registered
   component/preset only when authoring is requested. Verify the inserted key,
   editor availability and sample inputs before configuring the next widget.
3. Use the child's content editor for its data, document, actions and internal
   layout. Use the widget shell editor for chrome; use page canvas controls for
   placement and spans. A shell title does not rename a resource or operation.
4. Establish configuration ownership in components that support page configuration
   versus individual preferences. Page scope does not disable parent autosave.
5. Configure data and interactions, then choose visual treatment with
   `praxis-ui-product-design`. Check the child's internal layout separately from
   stacking its containing widget at a narrow breakpoint.
6. Verify settled runtime after Apply and acknowledged save/fresh reopen. A reset
   affects its documented scope; closing a clean inspector is different from
   undoing an already inserted/saved widget.

## Sources, Measures And Layout Choices

Page state, dataSources, transforms and derived measures are authorable only when
the installed editor actually exposes them. Inspect page settings and the State
section; distinguish guided controls from advanced JSON. Resolve the real
operation, field, response shape and target state path before using a query or
transform preset. Preserve false, zero, empty and error results. Do not invent an
active/inactive ratio for a nonboolean category or mistake fallback values for
successful reads. Follow Core's data-source contract for path/endpoint resolution;
the base-resource rule of a Table input does not redefine a page HTTP source.

Page layout presets describe roles/appearance and may preserve existing positions.
Arrange controls may redistribute existing widgets; they need widgets to operate.
A guided screen composer can create a different draft. Before adopting one, inspect
its registered IDs, schema assumptions, outputs and replacement behavior; a
"five-minute" label is not runtime certification or measured duration. Prefer
per-widget insertion when the composer cannot represent the requested semantics.
Do not use aliases or host registrations to disguise an unresolved composer ID.

For widget links use the composition skill's browser-connections reference.
Keep page values/derived data, transient selection and child inputs distinct.
Use a shared page source when it is an actual supported choice, not as a way to
bypass a child's validator or obscure what its editor will show on reopen.

## Evidence Required By The Requested Operation

Inspection: editor opens with the correct current target, controls and diagnostics;
cancel without changing values. Authoring: verify a changed value and its runtime
effect. Persistence: verify acknowledged save and reopened ownership/value. A
complete screen needs the agreed applicable operations exercised: for example
query/clear, selection/detail or permitted form actions. Populated widgets alone
do not prove those operations. A blocked API or absent editor remains
an explicit owner follow-up, not a reason to rewrite the host during a browser run.
